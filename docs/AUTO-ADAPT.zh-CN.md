# 有边界的本地自动适配

本功能用于更新后文件 SHA256 变化、但原修补仍可成立的情况。它自动检查和生成本次进程的地址配置，不会自动修复任意新缺陷。现有完整哈希白名单优先使用；默认不开启未知文件分析。

## 开启及关闭

需要完整源码仓库、Windows x64、64 位 Python，以及 `compatibility/requirements.txt` 中的精确依赖版本。`tests/test_native_patch.py`、`tests/test_nvidia_cleanup.py` 和它们依赖的仓库模块也是运行必需文件，不能删掉。现有信号量 ZIP 不提供此功能。

```powershell
py -3 -m pip install -r compatibility/requirements.txt
py -3 .\ld14-auto-adapt.py --enable
powershell.exe -NoProfile -File .\Manage-LD14-Guard.ps1 -Action Start
```

必须使用守护实际配置的同一个 Python；若依赖放在单独目录，沿用管理脚本的 `-DependencyDir`。这里的命令不会下载除所列 Python 依赖之外的补丁或程序。启用后本机配置保存 `auto_adapt: true`；下一次所选实例启动时自动重新检查。更换目录或实例编号仍需重新配置。

关闭时运行 `py -3 .\ld14-auto-adapt.py --disable`，再正常 Stop / Start 守护以重新加载设置。此操作不会撤销已写入当前进程的信号量补丁；实例退出后它自然失效。单独修改配置不会让已运行的守护热加载。

## 能自动接受哪些更新

| 组件 | 当前自动检查的边界 |
| --- | --- |
| renderer | 基于人工验证的 14.0.36.0 基线，匹配构造/析构及其直接代码依赖、导入 API、对象字段、分支和部分引用数据。函数可独立搬地址；间接代码指针的非图内目标必须保留原 RVA 和完整代码范围。歧义或不支持的布局拒绝。 |
| fastpipe | 非资源映像的实现、布局、导入和加载器元数据保持一致；允许不影响它们的版本资源、签名、时间戳及调试元数据变化。实现变化拒绝。 |
| NVIDIA | 当前基线为 621.01。复杂内部分发表尚不能可靠解析，所以只接受上述整幅非资源映像一致性检查。内部代码、TLS、堆布局或地址变化拒绝，不能自动迁移任意驱动新版。 |

renderer 的数据检查为有界窗口和地址关系检查，并非整个程序的形式化等价证明。程序其他行为和真实游戏负载仍需观察。自动检查成功不代表已证明长期内存稳定或黑屏消失。

## 自动检查顺序

1. 计算当前文件完整 SHA256，确认选定实例实际加载的是所选 LD14 的 fastpipe。LD9 不会因共享 renderer 而被选中。
2. 未知文件在独立子进程离线解析，单次上限 90 秒、单文件上限 128 MiB。基线文件有固定 SHA256，报告不会作为下次放行依据。
3. renderer 在自有测试内存执行 128 个原始和 128 个修补案例；驱动在自建临时子进程执行 9 个清理/所有权/脱离案例。此时不附加模拟器。
4. 再次计算文件和配对哈希，拒绝分析期间安装器替换文件的情况。生成的配置只在当前控制器内存缓存，绑定完整哈希。
5. 应用时仍检查目标运行时代码及引用指令，然后使用已有的进程内修补路径。不会修改磁盘厂商文件。

后台分析期间状态为 `checking_compatibility`，完成后应为 `active`，并有 `auto_adaptation.enabled: true`。命中人工白名单时 renderer / driver 的自动分析字段为 null 是正常的，表示不需要重新推导；未知文件成功时包含证明报告路径。

缺依赖、超时、解析不支持、多个候选、原生自测失败或运行时代码不符都会停止；守护不反复尝试同一个失败 PID，也不重启模拟器。原因写入 `logs/auto-adapt/*.json` 和 `logs/guard/status.json`。修复阻碍后需重新加载守护，或等待实例下一次正常启动。未知 fastpipe 若在启动配置检查阶段失败，控制器会以 `failed` 退出，需要手动 Start。

## 离线验证

可强制分析一个文件，即使其 SHA256 已在人工白名单中：

```powershell
py -3 .\ld14-auto-adapt.py --kind renderer --image '本机libOpenglRender2.dll路径' --pipe '所选LD14的gpu\fastpipe2.dll路径'
py -3 .\ld14-auto-adapt.py --kind driver --image '实际加载的nvoglv64.dll路径'
```

开发验证使用 `scripts/verify-auto-adapt.py --renderer 路径 --pipe 路径 --driver 路径`：仅在临时副本中改变时间戳来产生未知哈希，然后验证实现变化和 TLS 目录重定向被拒绝；原文件字节必须不变。日志、配置、DLL 和转储不加入 Git。新的人工基线只能由开发工具从指定的已验证文件生成，不会从用户未知文件自动学习。

2026-11-17 本机验证：52 项回归测试通过；临时真实 DLL 副本的 3 项兼容更新通过、4 项不兼容变化全部拒绝。另强制从当前真实 renderer 推导配置，22 个代码节点形成 33 段运行时 guard，对正在运行的已修补实例只读核对通过。守护重载后标记为 7、自动模式开启、两项补丁和 USB 保护均为 active，模拟器 PID 未变化。当前已知文件仍走人工白名单；尚未用未来未知正式版进行长期游戏验证。
