## 确认的信号量泄漏

`MyRenderThread` 构造函数位于 RVA `0x604e0`。它调用 `CreateSemaphoreW` 两次：

| 对象字段 | 初始计数 | 最大计数 | 原析构行为 |
| --- | ---: | ---: | --- |
| `this + 0x4b8` | 2 | 100 | 未关闭 |
| `this + 0x4c0` | 0 | 100 | 关闭 |

析构函数范围为 `0x60990..0x60b9c`。原来在 `0x60aff` 读取第二个信号量，并在 `0x60b06` 调用 `CloseHandle`。在该位置 RSI 已是 `CloseHandle`，RDI 为当前对象。

修补先跳到同一函数不可达的对齐空间，补充 `CloseHandle([rdi+0x4b8])`，再恢复第二个信号量的原有关闭路径。两个短代码段都位于原函数展开信息覆盖范围内。写入前暂停选定进程，发布跳转前完成辅助代码段写入，写入后核对和恢复页面权限。

### 验证证据

- 未修补：第一类信号量创建 223 个，观察到关闭 0 个；第二类创建 223 个、关闭 218 个。
- 受控界面操作：36 次析构均遗漏第一类信号量。
- 独立 Windows 原生测试：128 个原始案例复现遗漏，128 个修补案例关闭所有预期句柄。仓库保留无需厂商 DLL 的机器码片段回归测试。
- 当前本地修补实测：325 次析构，650 次创建和 650 次关闭，跟踪集合无残留。
- Android 离屏测试：30 轮 EGL 上下文、纹理、帧缓冲创建与销毁，实际像素检查通过。

修补不会猜测并关闭应用前已经泄漏的句柄；这些历史残留由正常退出进程释放。

## 内存问题仍然存在

历史 LD14 长时间运行约 17 小时后曾达到 89.92 GiB 私有提交、67,179 个句柄。同期开着的 LD9 约 10 GiB、2,900 个句柄。重启可释放大量累计提交，但不是缺陷修复。

在信号量补丁生效后，《碧蓝航线》实际运行、没有 Frida 或离屏测试负载的 Windows 外部采集中，约 70 秒内私有提交增加 334.98 MiB，总句柄减少 42 个。句柄泄漏和大额内存增长不能视为已被同一个修补解决。

这次约 79 秒的 ETL 记录 10,848 次分配、3,026 次释放。约 1.209 GiB 分配在窗口末尾未配对到释放。**未配对不等于永久泄漏；原始提交请求之和也不等于进程净增长。**

主要路径：

| 渲染器调用返回 RVA | 路径 | 当前解释 |
| --- | --- | --- |
| `0x26472d` | `glTexStorage2D` / NVIDIA / WDDM | 大块纹理存储分配，尚未证明遗漏销毁 |
| `0x3f51fc` | 压缩纹理处理中的计算任务 / NVIDIA / WDDM | 仍需追踪具体资源寿命 |
| `0x41cb8e` | `wglMakeCurrent` / NVIDIA 用户态分配 | 大量 64 KiB 块，值得优先分析 |

其中 `wglMakeCurrent` 路径约 291 MiB 用户态分配在窗口结束时未配对到释放，约 287 MiB 来自已经退出的短线程。十多分钟后的只读地址查询仍见私有提交，但不能排除地址重用。

### 已排除的简单推断

- 67 个辅助线程都成功解绑 WGL 上下文后正常返回，未观察到强制终止线程。
- 辅助线程未显式调用 `eglReleaseThread` 不能单独作为根因：当前 Windows 平台后续释放实现并不提供额外的回收。
- 已检查的 ColorBuffer 析构会调用纹理删除，GLsync 创建/删除也配对；不能直接断定纹理或同步对象漏删。
- 当前 FrameBuffer 映射和延迟销毁队列保持较小，未证明队列无界增长或溢出。
- 独立 WGL 的复用上下文、逐次销毁上下文、核心上下文绑定等 120 次短线程测试，在预热后基本稳定。它未复现实际雷电负载，不足以排除复杂负载下的驱动问题。
- 驱动配置查询未找到雷电专用的线程优化覆盖。

## 采集与修补边界

优先用外部 ETW/WPR 和只读进程统计保留增长窗口。全局 `NtAllocateVirtualMemory` / `NtFreeVirtualMemory` 的 JavaScript 注入探针曾使被测 LD14 失去响应；该方式已移除，不应照搬。

对第二处行为修补，需要能指向具体所有者的存活分配证据，或在基线失败、修补后通过的受控复现。当前尚无足够证据安全加入额外 GPU 释放调用。

黑屏历史涉及显卡恢复现象，但并非每次黑屏都已证明由这处泄漏引起。修改驱动超时、强制清工作集或定时重启只能被当作单独的缓解方案，不能记为根因修复。

## 2026-09-06：NVIDIA mimalloc 线程堆保留空页

### 长期运行后的状态

同一个已应用信号量补丁的 LD14 后端，在约 3 小时的两个观测点之间，私有提交从 4.49194 GiB 增加到 23.98384 GiB。后一个观测点为 01:19，补丁字节仍为 `patched`。句柄为 1,659，信号量为 110。

游戏退出记录在 01:14 显示 `USER REQUESTED / FORCE STOP`；捕获时已无游戏进程。该记录不能区分人工操作与自动化，但不支持将这次退出描述为 OOM 或崩溃。Android 可用内存约 3.14 GiB，宿主后端仍保留约 24 GiB 私有提交。

本地保存了一份 24.27 GiB 完整转储。以下分析没有在目标进程中执行释放操作。

### 可验证的内存归属

`nvoglv64.dll` 的版本为 `32.0.16.1664`，SHA256 为 `970bb2528b3c12867997ac1b344eb6b9b356e18bc8a1ad768238e3306b58a4c9`。驱动包含 mimalloc 诊断字符串，其内存池、页、位图及线程局部数据布局与 mimalloc 3.x 对应；结构对照使用公开源码 `v3.1.5`，不据此断言驱动采用了完全相同的上游版本。

11 个内存池的头部都指向驱动 RVA `0x2d2ed80` 的分配器子进程结构。它们共保留 24 GiB 虚拟地址，实际提交 **19.48480 GiB**。每个池的提交位图都与转储中的 Windows 内存区域信息逐项吻合。

| 分析对象 | 数量 / 大小 | 解释 |
| --- | ---: | --- |
| 驱动内存池中的已注册页 | 315,809 | 逐页验证内存池指针、slice 索引及页布局 |
| 不在存活线程默认 TLS 中的 backing heaps | 14,619 | 以实际 TLS 堆/TLD 身份核对，避免只用可复用的 TEB 地址判断 |
| 这些堆持有的页面 | 19.23157 GiB | 315,076 页 |
| 这些堆中扣除跨线程待收集释放后完全空闲的页 | **19.22180 GiB** | 314,930 页；逐条验证释放链的地址范围、对齐、无环及长度 |
| 这些堆扣除跨线程释放后剩余的对象块 | 约 1.20 MiB | 块大小统计，不等同于用户实际请求字节数 |
| 已交回内存池、但尚未解除提交的空闲 slice | 仅 1.0625 MiB | 与 19 GiB 异常不在同一数量级 |

当前存活线程的默认 TLS 对应 17 个仍持有注册页的堆；另有 3 个页头引用的堆，其 TLD 已清空，单独记录而不强行归类。14,636 个可解析 TLD 均指回预期分配器，且 backing heap 指针与被检查的堆一致。

这明确解释了主要保留机制：**大量已空闲页面仍挂在线程堆上，没有进入可供其他线程回收的状态，也没有交回内存池。** 它与之前 `wglMakeCurrent` 路径的 64 KiB 提交及短线程生命周期证据一致，但此前 ETL 与本次转储属于不同的后端进程，不能拿旧地址直接关联本次对象。

### 当时仍需确认的触发点

驱动的 PE 与转储中均存在 TLS 退出回调。回调 RVA `0xa86c10` 在 `DLL_THREAD_DETACH` 时调用 RVA `0xa7f2d0` 的 mimalloc 线程清理路径；该路径会读取默认 TLS 堆、检查当前线程身份，再收集/移交线程堆。

因此，不能将原因简化为“驱动没有线程清理函数”。单份转储仍无法区分：回调未执行、默认 TLS 堆提前被替换、线程身份检查导致提前返回，或者清理后又发生了分配并创建新堆。尚未完成能确认其中某一条路径的受控复现。

### 验证计划（已完成，见下文）

在一次短时、有边界的重现中，按线程实例记录：`wglMakeCurrent` 前后、辅助线程返回前、驱动 TLS detach 回调及 mimalloc thread-done 入口/出口的默认堆指针、TLD 地址和线程序号。重点检查默认堆何时发生替换，以及最后一次分配是否晚于最后一次线程清理。线程 ID、TEB、堆地址都可能复用，必须一起记录顺序和生命周期。

同时用只读内存池计数确认每轮退出后空页/残留堆是否增加。对照组包括复用同一线程以及相同驱动下的独立 WGL 负载。只有复现能证明特定清理点遗漏后，才实现新行为修补。

单独调整 mimalloc 的 `purge_delay` 或强制清工作集不能解决当前已证明的页面归属问题。也不能根据离线空页判断，直接在运行中跨线程调用 `VirtualFree` 或强制销毁未知堆。

参考源码：[arena/page 结构](https://github.com/microsoft/mimalloc/blob/v3.1.5/include/mimalloc/types.h)、[位图](https://github.com/microsoft/mimalloc/blob/v3.1.5/src/bitmap.h)、[线程堆清理](https://github.com/microsoft/mimalloc/blob/v3.1.5/src/init.c)、[Windows TLS 回调](https://github.com/microsoft/mimalloc/blob/v3.1.5/src/prim/windows/prim.c)。

## 2026-09-06：短时复现确认清理顺序失配

本节为上述离线分析之后的实时验证，解决了“最后一次分配是否晚于清理”的未知项。

先在独立 WGL 进程上验证原生探针。回调只写固定大小缓冲区，不在分配器或 loader 锁内执行 JavaScript 日志。测试显式等待 Windows 线程句柄结束，避免将 Python 的 `join()` 完成误当作 DLL 退出回调也已结束。32 轮新建核心上下文和绘制测试中，64 个线程堆全部进入清理路径，未出现晚于清理的新堆。

随后临时启动同一 LD14 实例，保留原有信号量补丁，运行 Android EGL 离屏测试。12 个绘制线程和 1 个进程辅助线程都出现以下顺序：

1. NVIDIA TLS 回调 `0xa86c10` 调用 mimalloc `thread_done`（`0xa7f2d0`），清理旧堆并把默认堆设为空堆。
2. Windows 随后调用同一个 DLL 的入口 `0x107d678`，进入 NVIDIA `DllMain`（`0xa22240`），原因仍为 `DLL_THREAD_DETACH`。
3. 在 `DllMain` 内发生新的 TLD/堆创建；退出 DLL 入口时默认堆仍然是这个新堆，之后没有对应清理。

例如一个线程先清理序号 25 的 TLD，随后在 `DllMain` 内创建序号 26 的 TLD。两代 TLD/堆复用了同一地址，因此只比较指针会漏掉这个问题。

这将原因定位为当前组合下的 **驱动内部线程退出清理顺序失配**，不是“回调不存在”，也不是原堆的线程身份检查失败。尚未确定雷电的哪些 OpenGL 使用方式使这一驱动退出分支发生额外分配；独立 WGL 对照中没有触发相同行为。

### A/B/A 对照

| 测试 | 新残留堆 | 页面 | 其中完全空闲的页 |
| --- | ---: | ---: | ---: |
| 原始清理，12 轮 | 13 | 245 | 14.5625 MiB |
| 线程退出末尾补充清理，12 轮 | 0 | 0 | 0 |
| 撤销补充清理，12 轮 | 13 | 245 | 14.6875 MiB |
| 封装原型，12 轮 | 0 | 0 | 0 |

每组 12 次像素检查均通过，没有丢失探针事件。对新建 TLD 的线程序号、owner TEB、backing heap 进行只读核对，遍历堆的 75 个页面队列，并检查跨线程释放链；没有结构验证错误或不可读元数据。B 组元数据已清空或重用，不能再找到本轮残留堆。

页面统计只描述本轮线程创建的堆，并不等于整个进程的净提交变化。注入、驱动缓存和后台活动都会影响短时 Private Bytes；本结论以堆身份与页面归属为依据。

### 实验修补

新增 [可选原型及安装说明](../experimental/README.zh-CN.md)。它在 NVIDIA DLL 入口完成 `DLL_THREAD_DETACH` 后，只对当前线程拥有的普通 backing heap 再调用一次驱动自身的 `thread_done(NULL)`。空堆和静态主堆跳过，线程归属不符则拒绝清理。所有 RVA 受精确驱动 SHA256 和运行时代码字节检查保护。

封装原型实时记录 34 次线程退出、13 次补充清理，归属异常和清理后仍被当前线程持有的堆均为零。脱离后核对驱动入口字节已恢复；随后正常关闭临时 LD14 实例。

最终另加了显式静态主堆保护，并在无 GPU 的原生夹具上检查九种输入情形，确认不误清理、保持原函数返回值，以及脱离时恢复入口。原型的真实游戏长时间运行、全部退出路径及其他驱动版本仍未验证，不能据此宣称所有内存泄漏或黑屏已经修复。

脱敏汇总：[validation-20260906.json](../experimental/validation-20260906.json)。现有 `v0.1.0-alpha.1` 发布包保持仅修补信号量；本轮没有发布新版本。
